# Multilingual App — Design Spec

**Date:** 2026-05-17
**Status:** Draft, pending implementation plan
**Scope:** End-to-end multilingual support across frontend, backend APIs, LLM outputs, and outbound channels (SMS, web-push) for all 10 currently supported languages.

---

## 1. Goals & non-goals

### Goals

1. Every user-visible English string in `web/` resolves through `t()` (no hardcoded literals in JSX).
2. `web/lib/bundles.json` is regenerated by an LLM-driven pipeline that produces **natural, sentence-level** translations (not word-for-word) for all 10 languages.
3. Language choice persists across reloads (localStorage for anonymous users, `users.preferred_lang` for logged-in) and drives TTS `speechSynthesis` + `SpeechRecognition` BCP-47 language attributes.
4. Outbound channels (SMS via Fast2SMS, web-push) deliver messages in the subscriber's preferred language using a server-side bundle store.
5. Dynamic API outputs are localized:
   - **Static catalogs** (disease names, crop names, soil types, treatments, prevention tips, market commodity names) — backend looks up canonical English ID in a translation table and returns the localized string.
   - **Free-form LLM output** (Gemini disease diagnosis, advice paragraphs) — the LLM prompt includes a language directive instructing the model to respond in the user's language using natural, farmer-spoken phrasing.
   - Numeric values and units (kg/ha, °C) stay untranslated; only labels are localized.
6. Frontend sends `Accept-Language: <lang>` on every API call via a single fetch wrapper; backend middleware reads it once and attaches `request.state.lang`.

### Non-goals

- No new languages beyond the existing 10 (en, hi, te, ta, kn, mr, bn, gu, pa, ml).
- No RTL layout support.
- No translation of user-uploaded content (photos, voice clips).
- No translation of third-party passthrough data (e.g., raw mandi names from government APIs) — wrapped in a best-effort lookup that falls back to the original string.

## 2. Architecture

```
┌─────────────────────────── web/ (frontend) ───────────────────────────┐
│  app.jsx ──► LanguageProvider (lang state + localStorage persist)     │
│      ├─► t(key) = window.makeT(lang)        ◄── bundles.json (10 lang)│
│      ├─► <Speak text lang={lang}/>          (TTS uses BCP-47 map)     │
│      ├─► SpeechRecognition.lang = bcp47(lang)                         │
│      └─► api.js fetch wrapper sets `Accept-Language: <lang>`          │
└───────────────────────────────┬───────────────────────────────────────┘
                                │  Accept-Language: hi
                                ▼
┌─────────────────────────── backend/ ──────────────────────────────────┐
│  middleware/locale.py  ─► request.state.lang  (validated, en fallback)│
│  services/i18n/                                                       │
│    ├── bundles/{en,hi,te,…}.json   ◄── shared catalog (server side)   │
│    ├── catalog.py    t(key, lang)                                     │
│    └── llm_prompt.py  language_directive(lang) → prompt fragment      │
│  routers/{disease,crop,market,soil}.py  ─► catalog.t() for labels     │
│  services/{sms,webpush_service,alerts}.py  ─► template via catalog.t()│
│  db: users.preferred_lang, alert_subscriptions.preferred_lang         │
└───────────────────────────────────────────────────────────────────────┘
┌─────────────────── scripts/i18n/ (build-time tooling) ────────────────┐
│  extract_strings.py     scan web/**/*.jsx for t('...') + raw JSX text │
│  translate_bundles.py   Claude API → context-aware translations       │
│  lint_bundles.py        CI gate: completeness + placeholder integrity │
└───────────────────────────────────────────────────────────────────────┘
```

### Key design points

- **Single source of truth for bundles.** Build script writes the same JSON to `web/lib/bundles.json` and `backend/services/i18n/bundles/`. Frontend and backend never drift.
- **`Accept-Language` everywhere.** One fetch wrapper sets the header; backend middleware stashes on `request.state.lang`. Routers read it — no per-endpoint plumbing.
- **Language persistence.** localStorage for anonymous; `users.preferred_lang` for logged-in. On login, server preference wins and overwrites localStorage; on change, both update.
- **Outbound channels** can't use `Accept-Language`; they read `subscriber.preferred_lang` from DB.
- **LLM-output localization is prompt-level**, not post-processing. Shared `language_directive(lang)` helper ensures every LLM call uses identical wording.
- **Translation pipeline is offline & reviewable.** Run by the developer, emits a git diff, eyeball + commit.

## 3. Data model & translation pipeline

### 3.1 Language codes

Canonical list — used by frontend picker, backend validator, bundle filenames, BCP-47 mapping. Single source: `scripts/i18n/langs.yaml`; codegen emits `web/lib/langs.js` and `backend/services/i18n/langs.py`.

| Code | Language    | BCP-47 | Native label |
|------|-------------|--------|--------------|
| en   | English     | en-IN  | English      |
| hi   | Hindi       | hi-IN  | हिन्दी        |
| te   | Telugu      | te-IN  | తెలుగు       |
| ta   | Tamil       | ta-IN  | தமிழ்        |
| kn   | Kannada     | kn-IN  | ಕನ್ನಡ        |
| mr   | Marathi     | mr-IN  | मराठी        |
| bn   | Bengali     | bn-IN  | বাংলা        |
| gu   | Gujarati    | gu-IN  | ગુજરાતી      |
| pa   | Punjabi     | pa-IN  | ਪੰਜਾਬੀ       |
| ml   | Malayalam   | ml-IN  | മലയാളം       |

### 3.2 DB migration

```sql
ALTER TABLE users ADD COLUMN preferred_lang TEXT NOT NULL DEFAULT 'en';
ALTER TABLE alert_subscriptions ADD COLUMN preferred_lang TEXT NOT NULL DEFAULT 'en';
```

### 3.3 Bundle file format

Migrate from flat `{key: "text"}` to structured:

```json
{
  "crop_get_rec_btn": {
    "text": "Get Crop Recommendation",
    "context": "primary CTA button on Crop Recommender form",
    "role": "button"
  }
}
```

Runtime `t()` reads `.text`. `context` and `role` are metadata for the translation LLM and human reviewers.

### 3.4 Translation pipeline

- **`scripts/i18n/extract_strings.py`** — walks `web/**/*.jsx`, finds `t('...')` calls plus raw JSX text nodes matching `>[A-Z][^<{]{3,}<` (flagged "needs wrapping"). Output: `scripts/i18n/extracted_keys.json` with `{key, file, line, surrounding_jsx_snippet, inferred_role}`.

- **`scripts/i18n/translate_bundles.py`** — for each `(lang, key)` missing or marked stale, sends Claude a batched prompt (~30 strings/call) with prompt caching on the rules + glossary block. Prompt rules:
  - Natural sentence-level translation, not word-by-word.
  - Vocabulary an Indian farmer actually uses.
  - Keep numbers, units (kg/ha, °C), and brand names untranslated.
  - Preserve markdown, `%s` / `{name}` placeholders, trailing punctuation.

  Writes to `web/lib/bundles.json` and copies to `backend/services/i18n/bundles/<lang>.json`. Emits `scripts/i18n/translation_report.md` (per-language diff for review).

- **`scripts/i18n/lint_bundles.py`** (pre-commit + CI) — every key in `en` must exist in every language; no non-en value may equal its en value; `%s` / `{name}` placeholders must match across languages; no language may have keys absent from `en`.

- **`scripts/i18n/glossary.yaml`** — pinned translations for terms that must be consistent app-wide (crop names, app sections, common verbs). Injected into every translation prompt to prevent batch-to-batch drift.

### 3.5 Backend localization catalog

Static content tables in `backend/services/i18n/catalogs/`:

- `diseases.json` — `{disease_id: {name: {en, hi, …}, treatment: {…}, prevention: {…}}}`
- `crops.json` — crop names + tips
- `soil_types.json` — soil names + advice
- `commodities.json` — market commodity labels
- `sms_templates.json` — outbound SMS bodies with `{placeholders}`
- `push_templates.json` — push title/body pairs

Separate from the UI bundle (domain catalogs vs UI strings) but go through the same `translate_bundles.py` pipeline.

## 4. Rollout plan

Six phases. Each is independently shippable; pausing between any two leaves the app working.

### Phase 1 — Foundation (no user-visible change)

1. `web/lib/langs.js` + `backend/services/i18n/langs.py` generated from `scripts/i18n/langs.yaml`.
2. Migrate `bundles.json` to structured schema via codemod; update `window.makeT` shim.
3. DB migration: `users.preferred_lang`, `alert_subscriptions.preferred_lang`.
4. `backend/middleware/locale.py` reads `Accept-Language`, validates, attaches `request.state.lang`.
5. `backend/services/i18n/catalog.py` — server-side `t(key, lang)`.
6. `web/lib/api.js` fetch wrapper adds `Accept-Language` header.

**Ship gate:** existing app still works in English, no regressions.

### Phase 2 — Frontend coverage

1. Run `extract_strings.py` to list unwrapped JSX strings.
2. Wrap pass for each view: `ViewCrop`, `ViewDisease`, `ViewMarket`, `ViewIrrigation`, `ViewAcoustic`, `ViewField`, `atoms`, `garden`, `Login`, `app`.
3. Persist `lang` in localStorage; read on init in `app.jsx`.
4. Wire BCP-47 to every `speechSynthesis.speak()` and `SpeechRecognition` instantiation.
5. Re-run extractor → expect zero remaining English literals.

**Ship gate:** every screen fully translatable; lint passes.

### Phase 3 — Translation quality pass

1. Seed `glossary.yaml` with ~30 core terms.
2. Run `translate_bundles.py --force-all` to retranslate all keys × 9 non-en langs.
3. Review `translation_report.md`. Spot-check Hindi/Telugu/Tamil. Iterate glossary, re-run flagged.
4. Commit refreshed `bundles.json` (both web + backend).

**Ship gate:** native-feel UI in every language.

### Phase 4 — Backend static-catalog localization

1. Build `backend/services/i18n/catalogs/` from existing data sources (disease data, crop labels, soil analyzer, market models).
2. Run `translate_bundles.py --target catalogs`.
3. Update `routers/disease.py`, `crop.py`, `market.py`, `soil.py`:
   - Read `request.state.lang`.
   - Return localized labels via `catalog.t()`.
   - Keep canonical English `id` field in response for client keys/logging.

**Ship gate:** API responses pre-localized; frontend stops post-translating API data.

### Phase 5 — LLM output localization

1. `backend/services/i18n/llm_prompt.py`:
   ```python
   def language_directive(lang: str) -> str:
       name = LANGS[lang].native_name
       return (f"Respond entirely in {name}. Use natural, conversational "
               f"{name} that an Indian farmer would actually speak — "
               f"not literal word-by-word translation. Keep numbers, "
               f"units (kg/ha, °C), and proper nouns unchanged.")
   ```
2. Inject into every Gemini/Claude call site (`routers/disease.py` photo diagnosis, `routers/soil.py` advice, any other LLM call).
3. Snapshot tests: same input → English vs Hindi response; eyeball quality.
4. Add response-language detector + single retry if model falls back to English.

**Ship gate:** LLM diagnoses arrive in user's language without breaking JSON-shape.

### Phase 6 — Outbound channels

1. Build `sms_templates.json` + `push_templates.json` with `{placeholders}`.
2. `backend/services/sms.py`: `body = catalog.t(template_key, sub.preferred_lang).format(**vars)`.
3. `backend/services/webpush_service.py`: same pattern for `title` + `body`.
4. `backend/services/alerts.py`: pass each subscriber's `preferred_lang` into send call.
5. Settings UI: language picker on subscription form (defaults to current app lang).
6. Audit Fast2SMS Unicode segment lengths — Hindi/Tamil = 70 chars/segment vs 160 for GSM-7. Trim templates or split.

**Ship gate:** SMS + push delivered in subscriber's chosen language.

## 5. Testing strategy

- `lint_bundles.py` runs in pre-commit + CI; blocks merges with missing/identical translations or placeholder mismatches.
- Backend pytest: parametrize endpoint tests over `[en, hi, ta]` × `Accept-Language` header; assert response strings match catalog.
- Manual walkthrough per priority language (en/hi/te/ta) before each phase ships.
- LLM-output snapshot tests for `disease.py` and `soil.py` covering all 10 languages.

---

## 6. Risks & mitigations

| Risk | Mitigation |
|------|------------|
| Fast2SMS Unicode cost — Hindi/Tamil ≈ 70 chars/segment, ~2× English cost | Phase 6 audits + trims templates |
| Gemini occasionally responds in English despite directive | Response-language detector + single retry |
| LLM mistranslates farming jargon ("blight", "tillering") | Glossary file pins canonical terms |
| Translation cost — 363 keys × 9 langs × Claude API | Acceptable (a few $ per full run); offline, run rarely; prompt caching reduces repeat-run cost |
| Schema migration of `bundles.json` could break consumers mid-deploy | Runtime shim accepts both flat and structured formats during transition |
